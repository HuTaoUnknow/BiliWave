# 本轮效率验证

2026-11-01。本轮在同一台电脑、同一 Qt 6.11.1 运行库上，对修改前冻结的程序片段与修改后的实现进行局部基准比较。使用独立临时 SQLite 和合成歌词，不读取实际乐库。

| 场景 | 规模 | 修改前中位数 | 修改后中位数 |
| --- | --- | --- | --- |
| 歌单统计与归属信息 | 600 首、24 张歌单、每单 80 首；重复 15 次 | 305.688 ms | 38.056 ms |
| 双语时间点查询 | 600 个事件，3000 次位置查询；包含新缓存生成成本 | 1150.392 ms | 0.964 ms |

前后各运行 3 次，交替执行，取中位数。所有运行的结果校验和均为 `6912085249`。原始记录、规模、每次耗时见 [REFACTOR_VALIDATION.json](REFACTOR_VALIDATION.json)。完整本机夹具与冻结基准保存在 `.cache/refactor-benchmark.cpp`、`.cache/refactor-before.exe`、`.cache/refactor-after.exe`。

## 原因

- 原歌单汇总先读全部歌单，再逐张读取完整歌曲并累加时长 / 收集归属；24 张歌单的汇总路径需要 26 次列表查询。现在歌单数量与时长由一次 SQL 聚合返回，归属 ID 单次查询，歌曲显示使用只取必要字段的摘要查询，共 3 次。测试不包含控件绘制时间。
- 原双语显示每个位置都遍历此前事件并判定语言。现在当前歌曲载入时生成每个事件对应的左右两句状态，播放或跳转时二分定位；缓存只针对当前歌曲，歌词或繁简设置变化时重建。位置更新同时取消读取歌曲 / 草稿数据库，偏移在歌曲变更时更新。
- 切歌只更新现有歌曲行高亮，避免重建浏览器和全部行按钮。乐库手动刷新不再重复重建未变化的播放队列。队列校验用一次有效 ID 查询代替逐条读取完整歌词。
- 调色板按主题初始化一次，绘制复用。构建将核心、服务与 UI 分层，应用和界面测试复用同一份 UI 对象，减少重复编译。

以上数字只代表两个计算环节，不能换算成整套应用、下载或 OCR 的同倍数提速。整体流畅度还受乐库大小、磁盘、显示缩放、音频设备和网络影响。本轮没有改变视频字幕分段 / 相似度算法，没有增加对在线服务的并发请求，也没有通过降低音质提速。
